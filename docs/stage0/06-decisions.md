# 06 · Decision log

| ID | Decision | Rationale | Revisit |
|---|---|---|---|
| D1 | **Monorepo:** `contracts/behest` (Rust, near-sdk 5.x, built with cargo-near), `services/executor` (TypeScript, Node), `apps/web` (Next.js + Tailwind using the Open Ledger tokens), `packages/` for shared types. pnpm workspaces | Rust has the best Chain Signatures tooling (`omni-transaction`) and the most mature testing (`near-workspaces`). One TS stack covers the executor and web app | — |
| D2 | **External chain for MVP:** Sepolia ETH (native only) | Simplest Chain Signatures adapter; no UTXO handling | Stage 2 adds Bitcoin testnet and ERC-20 |
| D3 | **One contract, many plans:** one plan per owner, keyed by owner account | Simple discovery and indexing | Stage 3 if multiple plans per owner are needed |
| D4 | **NEAR custody:** NEAR is deposited into contract escrow per plan; the owner withdraws freely with no open proposal | Contract can transfer NEAR directly without an executor | — |
| D5 | **Balance snapshot at proposal time**; withdrawals frozen while a proposal is open; later deposits not distributed in MVP | Matches the guardian-approves-a-snapshot model | Stage 2: recount and later-deposit rules |
| D6 | **ETH fee model:** fees paid from the vault; reserve `heirs × eth_gas_limit × max_fee_cap` at proposal; `max_fee_cap` and `eth_gas_limit` set by admin, gas limit snapshotted per proposal (was a fixed 21000 until Glamsterdam made first transfers to unused addresses cost ≈207k) | Heir needs no ETH; caps bound the cost | Stage 2: per-chain reserves and quotes |
| D7 | **Owner vault withdrawal** (shipped in Stage 2; deferred in the MVP): `withdraw_vault(asset, amount, to)` for ETH or a token, owner only, only with no release open or after it settled. It takes the next vault nonce through the normal signing and executor path (transfer index `VAULT_WITHDRAWAL` = `u32::MAX`). While one is unresolved, `propose_release` fails with `E_VAULT_BUSY`. The executor resolves it without the owner: it confirms it, retries fee failures, or burns a failed, never-broadcast withdrawal's nonce with a 0-ETH re-sign (`cancel_vault_withdrawal`) | Without it, unspent fee reserve and post-settlement remainders were stranded. The nonce-gap risk that made the MVP defer it is handled by the busy rule and the same-nonce cancel | — |
| D8 | **Executor:** team-operated, but contract-registered and replaceable; anyone can rebroadcast the public signed tx | Proves replaceability without building a market | Stage 3: second independent executor |
| D9 | **Upgrade and pause authority:** single admin account on testnet; pause covers new plans and new sign requests only | Speed for MVP; risk documented (05 #13) | Stage 4: time-locked multisig |
| D10 | **Privacy:** fully public plan data on testnet | Roadmap Stage 1 scope | Stage 3: commitments |
| D11 | **Notifications:** console/email from the executor; never affect contract state | Roadmap Stage 1 scope | Stage 2 workflows |
| D12 | **Rounding remainder stays in the vault/escrow** | No implicit recipient | Stage 2 explicit remainder rule |
| D13 | **Proposal rejection:** a proposal dies once enough guardians reject that quorum is impossible | Prevents a deadlocked proposal from blocking new ones | — |
| D15 | **ERC-20 adapter (Stage 2):** admin allowlist (≤ 4 reverting tokens; testnet WETH) stored outside the contract struct; transfers snapshot the token address; one fee reserve per vault transaction; same vault, nonce sequence, executor and recovery path as ETH | Reuses the proven ETH signing path. A second asset is needed for the partial-failure demo. No state migration needed | Per-plan token opt-in; balance proofs instead of reported balances |
| D16 | **NEP-141 adapter (Stage 2):** admin allowlist (≤ 4; testnet wNEAR) with each token's registration price; deposits arrive by `ft_transfer_call` (msg = plan owner), anything unlisted or for a plan with a release open is refunded by the token; escrow per token and plan under raw keys; split like NEAR among heirs with a NEAR destination; the contract registers each heir with the token (NEP-145) before paying, from NEAR reserved out of the plan at proposal time; listing a token registers the contract itself | Heirs need nothing, not even a token registration. No migration. Same claim/retry/cancel paths as NEAR | Reading registration price from the token at proposal time; per-plan token opt-in |
| D17 | **Release rules (Stage 2):** optional per-plan rules beside the plan (raw key, owner-set, frozen while a release is open, re-checked when heirs change): fixed amounts paid first in listed order and capped by what's there, then shares; a named heir receives each asset's rounding remainder (otherwise it stays, D12); a heir's share of 0 is now allowed. Unclaimed shares: a transfer still `Pending` one claim window after the plan becomes claimable can be moved by anyone to the heir's named alternate, and one window later to the plan's fallback. Only never-signed transfers move, so no ETH nonce or signature exists. Alternates and the fallback must be outsiders, so the current holder shows which step a transfer is at | Owners can express "100 NEAR to my nephew, the rest by share" and "if she never claims, to her brother, then to charity" without trusting anyone to redirect funds. Fixed and remainder amounts join the heir's single per-asset transfer, so no extra vault transactions or fee reserve | Redistributing unclaimed shares among the other heirs pro rata; reassigning transfers that failed rather than went unclaimed |
| D18 | **Delay signers (Stage 2):** optional per-plan set (≤ 10; never the owner or a heir, may overlap guardians and the UI says so) with its own quorum. While an approved release is waiting, one signer requests an extension (≤ `max_extension_ms`, optional public reason code ≤ 64 chars) and it applies when the quorum agrees; total extensions per proposal ≤ `max_total_extension_ms` (≤ 365 days). One request at a time; votes don't carry into a new proposal. The extension moves `waiting_ends_at_ms`, which is the owner's cancel window, the signing cutoff and the start of claiming | Matches the vision: a separate quorum that can only delay, within contract caps. Shortening is deliberately absent: the vision limits this role to extending. Reusing the single cutoff field keeps "nothing is signed before the owner's window ends" true by construction | Shortening a delay; evidence attachments; per-asset delays |
| D19 | **Release mode (Stage 2):** per plan, `Claim` (default), `Automatic` or `Hybrid` with a grace period, plus ordered overrides for one heir (or every heir) and an asset group (all, NEAR-side, Ethereum-side); the first matching override decides each transfer. A share reassigned to an alternate or the fallback follows the asset-group or plan mode. In Automatic (from the end of waiting) or Hybrid (after the grace) anyone may call `release(owner, heir)`, which starts that heir's still-pending transfers exactly as a claim would; the executor does this every tick. Heirs can always claim themselves. Destinations and amounts stay the approved ones | Heirs who never open the app still receive. The trigger carries no authority: it can only start what guardians approved, after the owner's window | Arbitrary per-asset lists instead of the two chain groups; automatic retry of failed NEAR transfers by third parties |
| D14 | **NEAR gas for heirs and guardians** is sponsored by a NEP-366 relayer in the MVP (revised; originally heirs paid) | People inheriting or vouching shouldn't need to buy NEAR first. The relayer only pays gas: it sponsors one allowlisted, non-payable Behest call per meta-transaction, only for the sender's actual role in that plan, with per-sender and global rate limits. The contract still authorizes every call. | Direct calls still work if the relayer is down |

## Deferred (explicitly)

Production timer values, attestations, guardian replacement while inactive, Bitcoin, privacy modes, and legal review. (ERC-20, NEP-141, release rules, delay signers and release modes moved into Stage 2 work: D15–D19.) See the roadmap stages.
