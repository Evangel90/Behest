# 05 · Threat model (MVP, testnet)

Severity is for a mainnet deployment of the same design. Status says what the MVP does about it.

| # | Threat | Impact | Mitigation | Status |
|---|---|---|---|---|
| 1 | Owner key compromised | Attacker edits heirs and withdraws | Out of protocol scope for MVP. Stage 3: high-impact edit notice and cooling-off | **Accepted (MVP)** |
| 2 | Guardian collusion (≥ quorum) while owner is alive | Premature release | Release requires `Overdue` first (owner must miss check-ins), then a waiting period during which one owner check-in cancels it. Funds can only go to the owner's chosen heirs | Mitigated |
| 3 | Guardians disappear (quorum unreachable) | Funds stuck | Never auto-lower quorum. Owner can replace guardians while active. Stage 3: standby guardians | Partly; documented |
| 4 | Guardian under-reports ETH, ERC-20 or BTC balance in the snapshot | Heirs receive less; remainder stays in vault | Nothing is redirected. The contract records every reported balance (`get_release_snapshot`) and the web app shows it next to the live vault before anyone votes, warning on any gap (over-reports too, which would make transfers fail). Whatever stays behind goes out in a follow-up round that heirs can start themselves (D21) | Mitigated |
| 5 | Malicious / compromised executor | False status reports, refusing to broadcast | Executor cannot alter payloads; signed tx is public in contract state so anyone can broadcast; executors are replaceable by admin | Mitigated |
| 6 | Replay / duplicate execution | Double payment | One fixed nonce per ETH transfer; NEAR transfers move to in-flight before the promise; callbacks are private | Mitigated (tested) |
| 7 | Signature before cancellation window ends | Irreversible early release | Contract checks `now >= waiting_ends_at` before every `sign`; `check_in`/`cancel` rejected from that instant | Mitigated (tested) |
| 8 | Payload substitution (recipient/amount/chain) | Funds redirected | Payload built inside contract from snapshot; no caller-supplied fields except a fee bump bounded by the cap | Mitigated (tested) |
| 9 | Proposal snapshot stale vs policy edit | Release to old heirs | Edits rejected while a proposal is open; proposal pins `plan_version` | Mitigated |
| 10 | Fee spike / fee exhaustion | Transfer stalls | Fee reserve at proposal; `FeeAboveCap` → retry later; funds stay in vault | Mitigated |
| 11 | Sepolia reorg | Status says Confirmed for a dropped tx | Executor waits N confirmations (default 6); retry reuses the same nonce | Mitigated |
| 12 | MPC timeout / failure | Transfer stuck in `Signing` | Callback failure → `Failed(SignFailed)`, retryable with the same nonce | Mitigated |
| 13 | Contract upgrade key compromised | Total loss | MVP uses a single testnet full-access key. Stage 4: time-locked multi-party upgrades, or lock the contract | **Accepted (testnet only)** |
| 14 | Admin abuse | Pause griefing; a false re-issue (see 20) | Admin can pause and re-issue a reverted transfer to its fixed heir and amount; no method changes recipients, amounts or plans | Partly (MVP) |
| 15 | Frontend compromised | User signs a malicious `set_plan` | Plain-language and rule view show the exact plan; wallet shows the call. Stage 3: signed builds | Partly |
| 16 | Demo timers in production | Releases in minutes | Timer bounds compiled in by feature flag; production build rejects demo durations (tested) | Mitigated |
| 17 | Heir loses destination key | Share unrecoverable | Destination fixed by owner; Stage 2 alternates/fallback | **Accepted (MVP)** |
| 18 | Unbounded storage growth / spam | Storage DoS | Caps on heirs/guardians; owner pays storage deposit at plan creation | Mitigated |
| 19 | Destination-chain gas rule change | Transfer reverts for out-of-gas; fee spent, nonce used | Configurable gas limit snapshotted per proposal; executor estimates before first broadcast and reports `GasLimitTooLow` instead of sending; same-nonce re-sign with a higher limit | Mitigated |
| 20 | A transfer is re-issued that didn't really revert | The original (still valid) and the re-issue could both be mined, paying that heir twice from the vault | **D22:** `reissue_reverted_transfer` needs a recorded proof of the revert. `prove_eth_outcome` checks Merkle-Patricia proofs of the transaction and its receipt against a block header, that the transaction is one the contract signed for the transfer's current nonce, and that the light client (`client-eth2.sepolia.testnet`) holds the header's hash as finalized. Anyone may prove or re-issue; a proof of success confirms the transfer instead, correcting a false "Reverted" report. Live `e2e-revert` | Mitigated (trusts the Ethereum light client's sync committee, not the admin or executor) |
| 21 | Malicious or non-standard ERC-20 | A token that returns `false` instead of reverting would look delivered when it wasn't. A token contract could also misbehave in other ways | Admin allowlist of at most 4 known, reverting tokens. Transfers snapshot the token address. The executor checks `to`, `value` and calldata against the snapshot | Mitigated (allowlist) |
| 22 | Guardian misreports a token balance | Over-report: that heir's token transfer can't be paid yet, and later vault nonces wait behind it. Under-report: tokens stay in the vault | Same model as `eth_balance` (D5). Guardians approve the exact transfer list, and anyone can check the vault. The executor simulates before broadcasting and reports `WouldRevert` without spending a fee. After a top-up, the heir retries at the same nonce, with no admin trust (live: `e2e-partial`) | Partly (MVP) |
| 23 | Owner withdrawal used to race or block a release | Withdrawing during a release would change heirs' amounts. An unresolved withdrawal could hold a nonce ahead of heirs' transfers | No withdrawal while a release is open (`E_PROPOSAL_OPEN`); no proposal while a withdrawal is unresolved (`E_VAULT_BUSY`). Executors resolve withdrawals without the owner, including a same-nonce 0-ETH cancel for one that can't go through | Mitigated |
| 24 | NEP-141 token misbehaves or registration price changes | A token could take deposits but fail transfers, or charge more to register a heir than was reserved | Admin allowlist (≤ 4). A failed token transfer stays `Failed` and is retried by the heir like NEAR; escrow isn't released until it confirms. Registration is attempted once per transfer and only if the reserve covers it; any unused reserve returns to the plan when it settles, and a cancel returns all of it. If a heir is already registered, the token refunds the deposit to the contract (not the plan): a small, bounded leak | Mitigated (allowlist) |
| 25 | Unclaimed share moved away from a slow heir | Anyone can move a heir's untouched share to the named alternate once the claim window passes, so a heir who is late loses it | Only to recipients the owner named, only after the owner-chosen window (production minimum 30 days, measured from when claiming opened), only for transfers never started; a claimed or failed transfer never moves. Rules are visible to guardians before they approve and can't change while a release is open | Accepted (owner's choice) |
| 26 | Delay signers stall a release | Colluding delay signers keep pushing the release back | They can only extend, never approve, cancel or redirect. Each extension needs their quorum and is capped; the total per proposal is capped (owner-chosen, ≤ 365 days). Every extension is public (`waiting_extended`) and notified to owner, guardians and heirs | Mitigated (bounded) |
| 27 | Third party triggers an automatic release | Someone starts heirs' transfers at a moment of their choosing | Only in modes the owner chose, only after the (possibly extended) owner window and any hybrid grace, and only the approved transfers to the approved destinations. Starting a transfer early is impossible; late just means the executor was down, and heirs can still claim | Mitigated |
| 28 | False or stale Bitcoin coins reported | A guardian reports coins the vault doesn't have, or that were spent, or overstates their value | Outputs (heirs, amounts, change to the vault) are fixed by the contract and the value is committed in every BIP143 signature, so a wrong value only produces an invalid tx; nothing can pay anyone else. Guardians approve the reported coins with the proposal. The executor checks each input before broadcasting and reports `Conflict`; a guardian rebases onto the real coins while nothing was broadcast | Mitigated |
| 29 | Two versions of a Bitcoin payout both confirm | A re-signed or rebased payout and an older signed version are both mined, paying a heir twice | A re-sign keeps the same inputs (identical tx or an RBF bump), so only one version can be mined. A rebase is refused once anything was broadcast and must reuse one of the old coins, so every new payout conflicts with every older one. Chained payouts reference the parent's txid, which is fixed before signing (SegWit) | Mitigated |
| 30 | Bitcoin payout stuck at a low fee | Fee spikes leave an earlier chained payout unconfirmed | Fees are reserved at the admin cap; the latest payout can be fee-bumped from its change (RBF), and an earlier one confirms once a later child pays enough (CPFP effect) or the network clears. Testnet only; the cap is an admin setting | Accepted (testnet) |
| 31 | A fee bump's earlier version is mined | The executor or contract treats the original as a foreign spend, cancels the withdrawal or strands later payouts | Replaced versions are kept on-chain; the executor reports whichever version the network holds and the contract adopts it only if it built it, moving the head to its change and re-signing later payouts from there. A withdrawal with a replaced version can't be cancelled | Mitigated |
| 32 | Contact details leak | Someone learns an owner's, guardian's or heir's email, chat or endpoint, linking them to a plan | Contacts never go on-chain; they live only in the notifier's database and are returned only to a session signed by that account. Logs carry account ids, never addresses. Webhook secrets are shown once. Operator can read the database (trusted for privacy, not for funds) | Mitigated (operator trusted) |
| 33 | Signed notifier request replayed or redirected | A captured signature re-adds a contact, or a signature made for another app is reused | NEP-413 recipient must be this notifier, the signed JSON carries account, action, arguments and a timestamp checked to ±5 min, and each 32-byte nonce is accepted once. Arguments come only from the signed text. Keys must be full-access keys of the account (RPC), or an unused implicit account's own key | Mitigated |
| 34 | Notifier made to call internal services (SSRF) | A webhook URL points at cloud metadata, localhost or the LAN | https only, ports 443/8443, no credentials in URLs, no redirects followed; every resolved address must be public, checked inside the socket's DNS lookup so a rebinding name can't switch to a private address after the check. Only `NOTIFY_WEBHOOK_ALLOW_INSECURE` (local development) relaxes it | Mitigated |
| 35 | Forged webhook calls | Someone posts fake "ready to receive" notices to a family's Slack or a heir's automation | Each subscription has its own secret; the body is signed with HMAC-SHA256 over `timestamp.body` and receivers reject stale timestamps. Notices only inform: acting on one still needs the contract, which can't be fooled by a message | Mitigated |
| 36 | Telegram link token stolen | Whoever opens the `t.me/…?start=` link first binds their chat to the victim's account and reads its notices | Tokens are random (192 bits), single-use, expire in 15 minutes, are stored hashed, and are issued only to a signed request. The bot replies with the linked account, the account's other channels are told a chat was linked, and the settings screen lists every chat with remove; `/stop` unlinks | Mitigated |
| 37 | Email bombing through confirmation mails | An attacker makes the notifier mail a victim repeatedly | Each confirmation needs a fresh account signature; at most 3 confirmation mails per address and 10 per account per day, per-IP and per-account request limits, and nothing but the confirmation is sent until the link is confirmed (a button, so link scanners can't confirm). Every notice has one-click unsubscribe | Mitigated |
| 38 | Notifier down or a notice lost | An owner misses a reminder; a heir doesn't hear a release is ready | Notifications never change contract state or deadlines; the web app shows everything. Deliveries retry with backoff and are recorded; restarts resume from the database. Owners are told not to rely on reminders alone | Accepted (by design) |
